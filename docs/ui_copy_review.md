# UI文言の確認と実装照合

UI文言を追加・変更・移動・転用するときは、Gemini に利用者視点の候補と懸念を求める。
実装担当は実際の挙動と本人の意図を優先し、自分の判断で提案を採用・調整する。
提案と判断理由を保存し、最終実装との一致を照合する。

## 入力と実行

1. `docs/evidence/ui-copy/<対象名>/request.json` を作り、`mode` を `proposal` にする。
   旧形式の例は [MAPペーストの記録](evidence/ui-copy/map-paste-pr456-2026-11-17/request.json)。
   `items` の各要素に、一意な `id`、候補の `text`、表示場所 `location`、目的 `purpose`、
   利用場面・表示条件 `context`、本人指定などの `constraints` を記入する。
   転用先も別の表示箇所として対象に含める。
2. 実装予定の文言や既存文言を `text` に入れ、表示場所と条件を具体的に伝える。
   最終文言は提案を受けた後に決めるため、`source` はこの時点では不要。
3. 既存の認証で `agy models` を確認し、利用可能な Gemini モデルを明示して実行する。
   新規認証、有料枠、APIキー追加を前提にしない。利用できなければ未確認として止める。

   ```sh
   python3 scripts/ui_copy_review.py run docs/evidence/ui-copy/<対象名> --model <利用可能なGeminiモデル>
   ```

送信するのは `id` から `constraints` までの6項目だけ。送信前に内容を読み、
秘密情報・個人データ・本番ログを含めない。CLI は空の一時作業ディレクトリで
plan / sandbox モードを使い、プロンプトでもツール実行・ファイル操作を禁止する。
既存のCLI権限を緩めたり、自動承認フラグを追加したりしない。

コマンドは `prompt.txt`、生の `stdout.json` / `stderr.txt`、`run.json` を保存する。
実行記録には指定ツール・モデル、UTC開始／終了日時、コマンド、終了コード、入力・出力の
SHA-256を含む。指定モデルとバックエンドの実モデルを区別し、応答から確認できない
バックエンドIDを推定しない。秘密情報などが出力された場合はそのままコミットせず、
証跡の安全な再取得まで未確認とする。保存済みの試行は上書きしない。

## 採用と最終照合

回答を読み、利用者がどう感じるか、実際の動作、本人の意図を踏まえ、実装担当が
各項目の最終文言を選択または調整する。Geminiの肯定や追加の確認往復は必須としない。

`adoption.json` の各 `items` に `id`、最終 `text`、判断理由 `reason`、該当idを含む
回答の逐語引用 `response_quote` を記録する。`source` に最終実装の相対 `path`、
一意な `start` / `end`、両端を含む `expected` ブロックを記録する。対象を識別する
要素や表示条件も含める。ソースは送信されずローカルで照合する。

```sh
python3 scripts/ui_copy_review.py check docs/evidence/ui-copy/<対象名>
python3 scripts/ui_copy_review.py check
```

前者は指定記録、後者は保存された全記録を照合する。CI の `release-sources` でも
全記録を確認し、後続PRの統合による文言・対象ブロックの変更を検出する。
表示文脈が変わった場合は、記録形式ごとに次のように対応する。

- `mode: proposal`：既存の提案が適用できるか判断し、必要なら新しい提案を取得する。
  適用できる場合は `adoption.json` の最終ソースと判断理由を更新する。
- 旧形式（`mode` 省略または `mode: review`）：ソースはハッシュ対象の `request.json` に含まれる。
  照合対象が変わったら新しいディレクトリで提案を取得し、採用後に旧記録を置き換える。

文言を削除した場合、`adoption.json` から項目だけを削除すると入力項目との照合に失敗する。
記録に残る対象がある場合は、残存項目で新しい記録を作成し、旧記録を置き換える。
記録の全項目が削除された場合は、その記録ディレクトリを削除する。残る全記録を照合する。

保存済みの実行証跡やハッシュを書き換えてはならない。旧記録はGit履歴に残る。
失敗した試行は一時ディレクトリに保持してPRへ原因を報告し、未完了の記録を
成功した記録として登録しない。

機械的に確認する範囲は、実行成功、証跡の完全性、入力と送信内容の一致、回答引用、
登録されたソース範囲と採用文言の完全一致である。これは電子署名や提供者の証明ではない。
提案の適用判断、対象の抽出漏れ、動的文言やブロック外の表示条件・
呼出元まで整合しているかは、実装者と独立レビュー担当が差分・画面文脈から確認する。
必要なブラウザー検証は既存の受入条件に従い、機能テストで文言確認を代替しない。

## 未確認の扱いと報告

CLI不在、失敗・タイムアウト、不正／空の応答、証跡不足、ソース不一致では
チェックが非ゼロ終了する。未確認の対象・理由・残作業をPRの「UI文言確認」と
完了報告に残し、機能の実装済みと文言の確認済みを分ける。提案を反映したと書くには、実行記録と判断理由へのリンク、最終照合結果、内容レビューの結果が必要になる。

この手順は文言抽出の完全自動化を行わない。登録外のUI文言もAGENTS.mdの提案取得の対象であり、
CI成功や既存表現であることだけを確認済みの根拠にしてはならない。
