# UI文言の確認と実装照合

UI文言を追加・変更・移動・転用する作業では、Gemini の回答と採用理由を保存し、
最終実装との一致を確認する。本人指定の文言・意図を優先し、仕様了承や既存転用を
確認省略の理由にしない。入口は AGENTS.md、報告欄は PR テンプレートに常設する。

## 入力と実行

1. `docs/evidence/ui-copy/<対象名>/request.json` を作る。
   [MAPペーストの記録](evidence/ui-copy/map-paste/request.json) が入力例。
   `items` の各要素に、一意な `id`、候補の `text`、表示場所 `location`、目的 `purpose`、
   利用場面・表示条件 `context`、本人指定などの `constraints` を記入する。
   転用先も別の表示箇所として対象に含める。
2. `source` にリポジトリ相対の `path`、一意な `start` / `end`、両端を含む
   最終実装予定の `expected` ブロックを書く。文言だけでなく、対象を識別する要素、
   イベント・表示条件など関連文脈を含める。ソース情報はローカル照合用で、送信しない。
3. 既存の認証で `agy models` を確認し、利用可能な Gemini モデルを明示して実行する。
   新規認証、有料枠、APIキー追加を前提にしない。利用できなければ未確認として止める。

   ```sh
   python3 scripts/ui_copy_review.py run docs/evidence/ui-copy/<対象名> --model <利用可能なGeminiモデル>
   ```

送信するのは `id` から `constraints` までの6項目だけ。送信前に内容を読み、
秘密情報・個人データ・本番ログを含めない。CLI は空の一時作業ディレクトリで
plan / sandbox モードを使い、プロンプトでもツール実行・ファイル操作を禁止する。
既存のCLI権限を緩めたり、自動承認フラグを追加したりしない。

コマンドは `prompt.txt`、生の `stdout.json` / `stderr.txt`、`run.json` を保存する。
実行記録には指定ツール・モデル、UTC開始／終了日時、コマンド、終了コード、入力・出力の
SHA-256を含む。指定モデルとバックエンドの実モデルを区別し、応答から確認できない
バックエンドIDを推定しない。秘密情報などが出力された場合はそのままコミットせず、
証跡の安全な再取得まで未確認とする。保存済みの試行は上書きしない。

## 採用と最終照合

回答を読み、各項目への肯定的な確認・指摘・条件を判断する。exit 0 や `SUCCESS` だけでは
文言確認完了にならない。本人指定と矛盾する提案は勝手に採用せず、必要な質問をする。
文言案を変える必要があれば、入力を更新した新しい試行で確認する。

`adoption.json` の `items` に、各 `id`、採用した `text`、採用理由 `reason`、
採用文言を含む回答の逐語引用 `response_quote` を記録する。最終実装へ反映したら実行する。

```sh
python3 scripts/ui_copy_review.py check docs/evidence/ui-copy/<対象名>
python3 scripts/ui_copy_review.py check
```

前者は指定記録、後者は保存された全記録を照合する。CI の `release-sources` でも
全記録を確認し、後続PRの統合による文言・対象ブロックの変更を検出する。
確認後に文言・表示文脈を変更したら、旧証跡のハッシュだけを更新して通してはならない。
新しいディレクトリで再確認し、採用できた記録に置き換える。旧証跡はGit履歴に残す。
失敗した試行は一時ディレクトリに保持してPRへ原因を報告し、未完了の記録を
成功した記録として登録しない。

機械的に確認する範囲は、実行成功、証跡の完全性、入力と送信内容の一致、回答引用と
採用文言の対応、登録されたソース範囲の完全一致である。これは電子署名や提供者の証明ではない。
回答が文言を肯定しているか、対象の抽出漏れがないか、動的文言やブロック外の表示条件・
呼出元まで整合しているかは、実装者と独立レビュー担当が差分・画面文脈から確認する。
必要なブラウザー検証は既存の受入条件に従い、機能テストで文言確認を代替しない。

## 未確認の扱いと報告

CLI不在、失敗・タイムアウト、不正／空の応答、証跡不足、未採用、ソース不一致では
チェックが非ゼロ終了する。未確認の対象・理由・残作業をPRの「UI文言確認」と
完了報告に残し、機能の実装済みと文言の確認済みを分ける。確認済みと書くには、
実行記録と採用理由へのリンク、最終照合結果、内容レビューの結果が必要になる。

この手順は文言抽出の完全自動化を行わない。登録外のUI文言もAGENTS.mdの確認義務の対象であり、
CI成功や既存表現であることだけを確認済みの根拠にしてはならない。
