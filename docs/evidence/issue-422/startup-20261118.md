# Issue #422 起動計測（2026-11-18）

Google Chromeのローカル開発ビルドで、操作可能になるまでの中央値は約0.20〜0.39秒短縮した。
Pythonランタイムとimportが引き続き最大の待機要因。今回の改善は、実行時に使わない
AIP原本を毎回取得・展開する経路を除き、起動工程を表示するもの。
実利用環境で報告された約15秒の再現・本番での短縮率を示す計測ではない。

## 条件と結果

- 変更前: `1b188c29`。変更後: このPRの実装。両方に一時的なPerformance markだけを追加。
- Google Chrome **158.0.8127.36**、headless、1440×1000、同じLinuxホスト上の
  `mcr.microsoft.com/playwright:v1.62.1-noble`。CPU・通信のthrottlingなし。
- 同じNode環境でLocal build、Pythonのloopback HTTP serverで配信。
  実jsDelivr/PyPIを使用し、request interceptionは使わない。
- 匿名、Firebase設定なし。認証欄はApplication context提示までの待機であり、
  Googleログイン済みAccountのネットワーク照合時間を測ったものではない。
- 0件と10件。10件は既存KML Goldenから作る合成Projectで、FTDのLast Calculationも保持。
  初回の合成データ準備・計算は起動計測に含めない。
- 各条件3回。coldはHTTP cacheを消してnavigate、warmは同じcontextで直後にnavigate。
  各条件でcold/warmを交互に実行。実機Safari、低速回線、端末CPU差は未計測。
- 最初の表示はFCP。操作可能はLeaflet zoom controlと有効なfile inputがあり、
  起動画面がなくなった時点。タイル画像の取得完了は操作可能の条件に含めない。

| Project件数 | cache | FCP 前→後 (ms) | 操作可能 前→後 (ms) | 短縮 |
| --- | --- | --- | --- | --- |
| 0 | なし | 64 → 48 | 3,779.5 → 3,385.6 | 393.9 ms (10.4%) |
| 0 | あり | 64 → 52 | 3,275.1 → 3,002.6 | 272.5 ms (8.3%) |
| 10 | なし | 64 → 56 | 3,706.1 → 3,494.4 | 211.7 ms (5.7%) |
| 10 | あり | 52 → 52 | 3,324.6 → 3,120.5 | 204.1 ms (6.1%) |

すべて中央値。生の個別値は [chrome-samples.json](chrome-samples.json)。
各groupの3回すべてで、変更後の操作可能時間は変更前の最小値より短かった。
少数回・非統制のネットワークを含むため、母集団に対する統計的有意差や
全端末で同じ短縮率が得られることは主張しない。

## 待機時間の内訳

0件・warmの中央値:

| 対象 | 変更前 | 変更後 | 解釈 |
| --- | --- | --- | --- |
| Application context提示まで | 24.7 ms | 23.8 ms | 匿名・Firebase未設定のみ |
| Pyodide/WASM初期化 | 904.0 ms | 909.5 ms | 今回の変更対象外 |
| パッケージ準備＋アセット取得・検証・展開 | 1,067.5 ms | 798.5 ms | 同梱量削減とインストール工程の集約 |
| Python import＋Application生成 | 1,209.0 ms | 1,186.9 ms | 支配的だが今回の変更対象外 |
| bootstrap応答後から操作可能まで | 42.6 ms | 52.4 ms | 一覧I/O、React/地図描画、100%の1frame表示を含む |

工程ごとの中央値の和は、全体時間の中央値と一致するとは限らない。
パッケージ工程の区切りはインストールをまとめたため変わっており、比較は
`packages + assets` の合計で行う。個別列を使って通信だけの短縮と解釈しない。
10件・warmではProject検証のWorker往復合計が155.9→167.3 ms。
検証は今回の条件では主因でなく、一覧の全件検証とAccount境界を維持した。

Python内の一度のcProfile診断ではimport時のPydantic構築とソースコンパイルが大きかった。
プロファイラ自体に負荷があるため、その値を上表の性能比較には使わない。
Pydantic `defer_build` とPyodide `packages` optionは予備比較で採用根拠となる
短縮が得られず、製品には導入していない。

## 配布対象の根拠

`data.zip` はfixture込みで **23,921,757 → 10,311,611 bytes（56.9%削減）**。
`LocalApplication.__init__` が読む4領域を同梱する:

- `data/performance`
- `data/reference/default`
- `data/reference/rjfm`
- `data/reference/rjfm-inbound-guidance`

AIP原本ZIPは[MAP原本の取込状況](../../reference/aip_map_geodata_20261029.md)で
runtime正規化が未完了とされ、現行LocalApplicationからも参照されない。
原本はRepositoryに保持し、Local配布物からだけ除く。VREPは既存のVite importで
JavaScriptに組み込まれる。RJFM inboundのPDFは実行時のSHA-256照合に必要なので残す。
縮小したarchiveだけから実LocalApplicationを初期化する回帰テストを追加した。

## 再計測

使い捨てcheckoutで [instrumentation.py](instrumentation.py) を適用してLocal buildし、
前後を別loopback URLで配信する。リリース用sourceに計測markを残さない。
Chromeと既存Playwright依存を利用できる環境で:

```sh
python docs/evidence/issue-422/instrumentation.py /path/to/disposable-checkout
# checkoutごとに AUTONAVLOG_TEST_FIXTURES=1 npm --prefix web run build:local
BENCHMARK_ORIGIN=http://127.0.0.1:4179/ node docs/evidence/issue-422/benchmark.mjs /tmp/before-0.json 0
BENCHMARK_ORIGIN=http://127.0.0.1:4178/ node docs/evidence/issue-422/benchmark.mjs /tmp/after-0.json 0
# 最後の引数を10にして、計算結果付きProjectの条件も同じ手順で測る。
```

生HAR・実Account・個人Projectは使わない。手動計測用のscriptであり、CIに時間閾値を追加しない。
本番公開・実機受入は本PRのローカル検証と区別する。
