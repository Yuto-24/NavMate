# Issue #422 起動時間の比較（2026-11-18）

変更前 `ba0803ed` と変更後 `f2120087` のLocalビルドを交互に測定し、主要画面の操作可能状態までの
中央値が全4条件で6.7〜7.9%短縮した。比較した20組はすべて変更後の方が短かった。
この結果は下記の隔離環境に限る。Issueにある過去の約15秒の観測を再現したものではない。

## 条件と測定方法

- WSL/Linux上のDocker、`mcr.microsoft.com/playwright:v1.62.1-noble`、
  Chrome for Testing 151.0.7922.34（headless）、1280×900、Pyodide 0.27.7。
- 同じ依存関係・テスト用気象fixtureでビルドした変更前後の成果物を、別ポートの
  loopback HTTPで配信。最終比較の両ビルドに一時的な計測コードは含めていない。
  CPU・ネットワークのthrottlingは行わず、このタスクの重い検証と同時実行しなかった。
- `issue_43_golden.kml`から作った有効なProjectを複製し、0件／20件を各試行前に
  新しいブラウザcontextのIndexedDBへ用意。名前・ID・tokenを分離し、checkpointを持たせた。
  Last Calculationは含まない。実利用者の保存領域やProjectは使用していない。
- キャッシュなしはCDPの`Network.clearBrowserCache`後のnavigation、キャッシュありは
  同じcontextでのreload。IndexedDBは維持する。各条件5回、奇数回は変更前→変更後、
  偶数回は逆順で実行した。
- 最初の表示はPaint TimingのFCP。操作可能状態は、bootstrap後に表示される
  経路作成見出しをMutationObserverで検出し、次のanimation frameの時刻を記録した。
  地図タイル全件の通信終了を操作可能時刻にはしていない。
- 認証設定なしの端末内利用で比較した。外部Google認証・Firestoreの実通信時間は
  この測定の対象外。アカウント切替・失効等は回帰テストで別に検証する。

各試行の数値は[比較データ](startup-422-20261118.json)に保存した。

## 支配的な工程と変更理由

事前の一時計測では、Pyodide/WASM初期化に約1.1〜1.7秒、後続パッケージに約0.5〜0.7秒、
PythonのimportとApplication生成に約1.2〜2秒を要した。importと生成を分けた試作では、
importが約1.2秒、生成自体は約0.1秒だった。今回の20件のProject検証は合計約0.1秒で、
これを省略・遅延して操作可能にする理由はなかった。認証設定なしの初期化は数〜数十msだった。

Pyodideの標準`packages`オプションでWASM初期化とパッケージ取得を重ねた。
導入済み0.27.7のAPI説明に基づく変更で、依存パッケージや整合性検証は減らしていない。
ただし、この変更だけの交互比較では冷キャッシュで約0.1秒の短縮、温キャッシュでは
明確な改善なしだったため、これだけを最終的な改善結果にはしなかった。

追加調査で、`prepare_local.py`が未加工のAIP原本も起動用ZIPへ入れていると判明した。
`reference/aip`は現行のLocal計算が使わず、MAP取込は#149の未完了範囲である。
この保管領域だけを配布対象から外し、ZIPは23,921,757→10,319,089 bytes（56.9%減）となった。
原本はリポジトリに保持する。RJFM帰路計算で検証する原本PDFや、他の参照・性能データは維持する。

変更後の0件・各5回の工程中央値は次の通り。製品のWorker進捗通知を外部から記録したもので、
各工程の中央値の和と、全体時間の中央値は一致しない。

| 工程 | キャッシュなし | キャッシュあり |
| --- | --- | --- |
| Pyodide/WASMとパッケージ準備 | 1,584 ms | 1,238 ms |
| 追加依存の読込 | 351 ms | 215 ms |
| Local資材の取得・検証・展開 | 241 ms | 230 ms |
| Python importとApplication生成 | 1,153 ms | 1,155 ms |

Python初期化が引き続き大きな待機要因である。UIの先行表示だけを操作可能と数えず、
保存済みProjectの検証を終える既存の境界を保った。React／地図の初期描画までを全体時間に
含めるが、個々のReact componentやタイル描画のCPU時間を分離した値ではない。

## 配布と予備APIを同時に確認する理由

以前の`calculation_contract`も`reference`全体をhashしていたため、ZIPだけからAIP原本を
除くと、ブラウザと予備計算サーバーの`data_sha256`が一致しなくなる。
配布と照合が同じファイル列挙を使うようにし、展開後のデータとサーバー側の契約一致、
必要な原本PDFの変更が識別値へ反映されることを回帰テストで確認する。
エンジン・データ不一致の拒否は維持し、異なるリビジョンの予備サーバーとの互換性を緩めない。

## 適用限界

低速回線、実機Safari、実利用者の大量Projectや大きなLast Calculation、実Google認証の
所要時間はこの数値から推定しない。認証・復元・保存・同期・数値計算・通信失敗の回帰は
既存スイートで確認する。進捗表示は時間予測ではなく、測れる取得量と完了工程による目安である。

計測用コードは製品へ残さない。再測定時も同じProject内容・件数、キャッシュ条件、描画の
完了条件、交互順序を揃え、同時に重いビルドやテストを走らせない。
